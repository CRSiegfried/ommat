# Changelog

All notable changes to ommat are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, a minor release may break the API; each break is listed under **Changed** or **Removed**.

## [Unreleased]

### Changed

- The ready sources that name no oracle form one batch each round, under `default`, where each was a call of its own. The idia binding sends the sources of one call that share an equal state and options as one idia request; a source whose joined request the provider's preflight refuses goes alone, and so does one whose state differs.
- The policy is an ordinary rule, and its estimate is the turn's decision. A design names it as `Design(policy="d:<name>", rules={...})`, the `d:` ref of a function rule or a table it declares; load refuses a design with no policy, and a policy ref with a field path, with no provider, or that is grounded; any rule, table, source or `when` may read it as it reads any `d:` ref. Interpret fires it as any rule, and at a cut its drain fires every rule not yet fired, so every turn decide returns holds the policy's entry; its failures are any rule's. `Decision` holds the record alone and reads `estimate`, the policy's entry as a value or a rebuilt marker, and `design_hash` from it. A turn is undecided when the decision is a marker; `escalation(record)` gives the marker's kind, its cause, its root cause, found by following `required` causes to the entries they name, `defect`, whether the root cause is a `raised`, `invalid-return` or `undeclared-read` naming a rule or the codec, and the record hash, so a caller routes a defect apart from a turn it hands on. A broken entry writes `t:state` and then the policy's entry `Unavailable` with the entry cause, runs no interpret and writes no `cause` item.
- Record format 8: the `settings` item names the `policy`; each turn decide returns ends at the policy's entry; the log holds no `plan` or `verdict` item and no `cause` item but `cancelled`; and a `calls` entry's `usage` keys are the closed set `input_tokens`, `output_tokens` and `passes`, interpret writing `usage` null, its repr under `invalid`, for any other. Records of formats 1 to 7 read as before. Design format 10: the document's `policy` is a string ref; load reads format 10 alone and refuses every earlier format with check 11, naming it.
- The views and renderers show the decision. `transcript`'s `decide` is `{"id", "board", "decision"}`, the board leaving out the policy's entry, and its `design` member is `{"hash"}`, where 0.4.0 had `{"name", "hash"}`; the renderers' decide call takes the board and returns `{"decision"}`. Each view gives `None` for a record before format 8. The lens shows the decision, and a record before format 8 as its entries and calls alone.
- Replay and the evaluation jobs read the decision as the policy's entry. Replay returns `wrong-design` for a record before format 8, `unfinished` for one that holds no policy's entry or holds a `cause` item and `nothing-to-replay` for a marker at `t:state`, needing no codec. `FindingKind` gains `wrong_design`. Every evaluation job refuses a record before format 8 as `wrong-design`, after `invalid-record` and before any replay. The dead-question lint and question reach compare decisions by the canonical bytes of the policy entry's value or marker, cause and refs included, and the lint raises `ValueError` naming the point when a run's turn is a broken entry (its `t:state` entry a marker); a policy that returns any marker of its own is compared. `switching_values` reports the policy's entry as the decision, always listed and compared with its whole cause; its store entry is at format 2, `{"unseen", "entries"}`.
- Replay checks each source it asks against the base record, the record whose calls answer, and answers no stale question. A ref is stale when the base holds no answer for it, as for a source or ref the record never asked or a `Failed` call that cannot be given back whole; when a need's value differs from the base's entry, wording and per-candidate slots included; or when its question's kind, labels, value type, list flag or identity differ from the call item's. A stale ref gets no key, so it is written `not-returned`, and is named by one `stale-question` finding, `{"kind", "ref", "source", "clause"}`, its clause `no-answer`, `needs`, `question`, `payload` or `oracle`. It replaces `not-in-record`, `ref-not-in-record` and `question-changed`; a reworded question is no longer answered from the old answer. Given the base's design, as `intervene` is, the check also stales a `t:` ref whose declared type differs (`question`), and every other ref of a source whose payload differs (`payload`) or whose `oracle` key differs or that `intervene` asks afresh (`oracle`). `intervene` checks against the record as read, so an edit to a need, such as a `t:state` field a source needs, stales that source where its old answer was reused; an entry an edit set is never checked, and a call an edit failed comes back failed only when asked whole. Deciding inputs, question reach and switching values count `stale-question` alone as undetermined. `from_record` shares the check, so it also refuses a question whose identity differs.
- `intervene`, `deciding_inputs` and `switching_values` load an edited design with `loaded`'s own callables when `functions` is `None`, so a design whose rules are lambdas or closures needs no `functions` passed; given `functions` still override them.
- `dead_questions` also compares two runs that agree on every other read and hold each grounded entry at its first point, whatever entries each grounds, so a question whose answer changes a candidate set, such as a gate a finder rule reads, can be `live`.
- `intervene`'s refusal for a constant rule whose output is the string `Unsure` and whose design does not load ends "; Unsure is given as the class ommat.Unsure, not the string".
- `load` no longer refuses a decision table or a data rule. `Table` copies its sequence fields when built.
- `dead_questions` takes a `values` key for a label question with no grid entry: its list is the labels to try, each at 1, in place of every label, so a question of many labels no rule bounds costs only the labels a caller names. Its report gains `narrowed`, those questions in code-point order. A key for such a question was a `ValueError`; a key for a question the grid fills still is.
- Design format 8 and record format 7: a `candidates` member may name a candidate field, and the `settings` item holds `sets`. A record of formats 1 to 6 reads under its own rules, and the ledger refuses `sets` in one.

### Added
- Combining designs in `ommat.helpers`: `combine(*parts, bind, policy, name=None)` unions parts, each `Part(design, ports)`, its ports the `d:` refs it reads and no declaration of it provides, into one design under a top policy, renaming nothing. `bind` gives each port a rule or table, or a `d:` ref the port takes through a pass-through table. It raises `InvalidCombination`, its `failures` each a `CombineFailure`, listing every failure: parts whose states differ, an id or parameter path two parts declare, a type, group, target or class tree two parts declare differently, a port a part provides, an unbound port and a bind key that is no port, among others; a type, group, target or class tree declared alike is kept once, and load checks the rest. `standalone(part, ports=None, *, given=())` gives each port in `ports` a constant and each port in `given` a value each turn from the source `ports`, under the oracle `ports`, so a part loads and decides alone. The guide [Combine small designs into one](docs/how-to/combine-designs.md) shows a workflow selector and a workflow asked in one call.
- The question-reach job in `ommat.evaluation`: `question_reach(records, loaded, *, values=None)`, async with a `_sync` twin, asks the dead-question lint's question from recorded turns, for a design whose cross product of read points is too large to run. For each record in list order, and each `q:` entry a returned call wrote, in log order, it sets the entry, as `intervene` sets one, to each of its declared question's read points other than its recorded value or marker, a grounded entry's own marker last, a candidate-valued question's each fixed label and then the first candidate at 1 over the labels the call asked, and replays once per point. A trial whose replay reports `stale-question` is undetermined, and any other reaches when the decision it wrote differs from the record's. It returns `{"records", "trials", "questions": {ref: {"status", "witness"}}, "narrowed"}`, each `q:` ref a source provides `live`, with the first reaching trial's record hash, entry ref and value as its witness, `not-determined`, `no-change-found` or `never-asked`. `values` is checked as `dead_questions` checks it, its keys `q:` refs, before any record is read; each record is then refused `invalid-record`, `unfinished`, `nothing-to-replay`, `wrong-design` or `baseline-differs`, naming its turn, before the next is read and before any trial.
- `ommat.helpers.top(r, ref, *, tie="abstain")`, the top label of an answer and its probability; at an exact tie it abstains, or with `tie="first"` gives the tied label first in the answer's `labels`. The helper version is 4, so a record written under version 3 replays with a `helpers-mismatch` finding.
- `ommat.bindings.fixed(values)`, a binding to no provider answering each asked ref from a mapping, for a fact the caller holds, such as the date, or a test's scripted answers; an asked ref it does not hold is `unsupported`, with a line of `warnings`.
- `defects(record)`, every entry whose cause is a defect by `escalation`'s test, whatever the policy gave, so a rule that raised on a decided turn is found, and `None` for a record before format 8; and `Record.entries`, each entry item by its ref, for a record of any format.
- The gold-answers job in `ommat.evaluation`: `write_gold_answers(gold_set, records, labels, *, results, copy_from=None)`, sync, writes a labeller's labels, `labels` as `{turn_id: {ref: label}}`, for the `q:` entries the calls of `records` wrote, as format-2 `gold-answer` entries keyed by the gold set, the question identity from the call item, the turn id and a grounded ref's candidate, and returns them. A label is a name of the question's labels, a candidate-valued set's from the set's entry in the record, never a description, or an extraction question's `{"value": v}`; `None` writes nothing. With `copy_from`, a key given no label takes the old set's label, a format-1 one included. An unfinished record is refused, and a copied label is checked as a given one. Every record is read, every label checked and every key looked up before the first write; the writes themselves are not atomic across keys. `RefusalReason` gains `invalid-label`, `conflicting-labels`, `unknown-entry` and `empty-copy`.
- The switching-value job in `ommat.evaluation`: `switching_values(record, loaded, path, *, functions=None, results)`, async with a `_sync` twin, replays a record under each value of the parameter leaf at `path`, each value's design `loaded`'s document with the leaf replaced, loaded with `functions`, or `loaded`'s own callables, and kept nowhere, and writes and returns one `switching-value` entry keyed by the record hash, the design hash and `path`. A numeric leaf, or interval, is probed in two rounds at the values the turn compares it against, a table cell's input, a `candidate` read's members included, a pick helper's label probabilities for `bar` and `thresholds`, the lead for `margin`, `p_null` for `extract`'s `null_bar`, and a function rule's reads its `boundaries` field names, with the lints' gap and end values, and on an integer axis the integers either side of each; round 1 adds the values round 0's replays recompute, and a component comparing a value only round 1 finds is listed in `unseen`. An entry's result is its value, or its marker's kind and code; every ref some run changed is listed, a not-determined run included. It gets switching values, the slacks of its own class, and classes. A `boolean` or `label` leaf is tried at every value and partitioned, and a numeric mapping has each key varied alone. An entry a matched table row passes the leaf through as `Param`, in any run, `carries` it; `unseen` is empty only when every way the leaf reaches a component is a comparison the job probed: it also names the function components declaring the leaf whose `boundaries` field does not name it, a `C+`, `C<` or `C>` table aggregating a `Param` of it beside another row, each reader of an entry holding the leaf, and each component a load failure names; a run that leaves the record is `not-determined` and a value that fails load `not-loading`. `RefusalReason` gains `unknown-path`, `unsupported-leaf` and `unrepresentable-slack`; `baseline-differs` is shared with the deciding inputs, and neither job counts a `helpers-mismatch` alone as one.
- The deciding inputs in `ommat.evaluation`: `deciding_inputs(record, loaded, ref, *, functions=None)`, async with a `_sync` twin, maps each declared read of the rule providing the entry at `ref` to `deciding`, `not-deciding`, `markers-only` or `not-determined`, by whether some single intervention on the read, as `intervene` makes one, changes that entry's value, or its marker's kind and cause code. A `q:` or `t:` read is tried through its entry, a grounded declared ref's through each of its entries, at each marker a binding may return and the record's format holds, a `q:` answer at `refused` only, a `t:` entry also at each value of a finite type, and its call failed with each structural code when every entry that call wrote is of the read's declared ref; a `t:state` field at each value of a finite type; a `d:` read by a constant rule at `Unsure` and each value of a finite type. A finite type is `boolean` or a label, either nullable. An intervention the form refuses at its target is not run, and one whose replay leaves the record is undetermined; a read with no intervention run, or with one undetermined and none deciding, is `not-determined`. A field-path read of a `t:` or `d:` entry is tried through the whole entry. Each intervention is single, so `not-deciding` says no single intervention changes the entry; joint effects are not explored. It refuses as `intervene` does, then `not-found` for a ref that is no entry of the record a rule provides, then `baseline-differs` when replaying the record under `loaded` gives any finding but `helpers-mismatch`, which notes only the helper version.
- Many turns in `ommat.helpers`: `decide_many(states, loaded, bindings, *, concurrency, settings=None, codec=None, observer_for=None)`, async, decides one turn per state, at most `concurrency` at once, and returns each `Decision` or `TurnFailure` in input order, a repeated state decided each time. A turn ended alone, by an entry refusal, an observer's raise or its own cancellation, is collected with its record so far; cancelling the run, or a `BaseException` that is not an `Exception`, aborts it.
- Read points in `ommat.helpers`: `points(loaded, ref, *, values=None)` gives one read's points, the values the lints range it over, in their order and record form. Question reach builds its trials from it. "Lint points" are now "read points".
- The answers table in `ommat.evaluation`: `answers(records, loaded, *, gold_set=None, results=None)`, sync, gives one row per question a call answered in each record, per candidate for a per-candidate question: the answer or marker, the top label, the question's targets and the groups naming it with their reasons; with a gold set, the gold answer and whether the answer erred, a missing gold answer kept as a row. A record of another design is `wrong-design`.
- The gold record in `ommat.evaluation`: `gold_record(record, recorded_design, gold_set, *, results, rerun_design=None)`, async with a `_sync` twin, replays a recorded turn with every question it asked set to its gold answer, so its decision is what correct answers lead to under the design. A question with no gold answer is stale and listed in `missing`. It returns `{"record", "findings", "stale", "missing"}`.
- Live scenarios in `ommat.evaluation`: `scenario(record, recorded_design, interventions, bindings, *, rerun_design=None, functions=None)`, async with a `_sync` twin, is `intervene` with each stale source asked of `bindings`, whole, and every other answer pinned from the record. A mixed call keeps the live provenance and its warnings name the base record and each pinned ref; a live failure fails the whole call. The turn runs on a live clock under the base's settings with no forced cut. It returns `{"record", "findings", "stale", "pinned"}`.
- Do-and-diff's scenario with no live binding in `ommat.evaluation`: `intervene(record, recorded_design, interventions, *, rerun_design=None, functions=None)`, async with a `_sync` twin, replays a copy of a recorded turn once under a list of interventions, under `rerun_design`, a design the caller built, when given; `recorded_design` is the design the record was decided under. An intervention sets a `q:` or `t:` entry a returned call wrote to a value or to a marker a binding may return (`{"ref", "value"}`), pinning it; sets a returned call to `Failed` with a structural code, every entry it wrote `Unavailable` (`{"source", "code"}`); sets a `t:state` field (`{"path", "value"}`); replaces a rule by a one-row table outputting a value or `Unsure` (`{"rule", "output"}`), the rules so replaced loaded in one document; or asks a source afresh (`{"ask"}`), staling every ref of it. The targets are disjoint, so the list's order changes nothing. A record edit is made on a copy of the record, which gets its own `hash` and is read back through `read_record`. It returns `{"record", "findings", "stale"}`, the replay record, replay's findings and the stale refs; the edited copy is not returned. An empty list with `rerun_design` given replays under it alone. `RefusalReason` gains `null-call`, `failed-call`, `marker`, `nonconforming`, `fault-code`, `not-found`, `candidate-rule`, `invalid-edit`, `no-edit`, `duplicate-target`, `conflicting-edits` and `invalid-design`.
- The design store and the evaluation store in `ommat.evaluation`. `DesignStore(root)` keeps a loaded design's document under the design hash it carries, at `sha256/<hex>`, accepting the same bytes again and refusing others with `held-mismatch`, and `fetch(key, *, functions=None)` gives it back through `load`, refusing a malformed key with `bad-key`, a key not held with `not-held` and bytes that hash to another key with `hash-mismatch`. `EvaluationStore(root)` keeps write-once entries `{"kind", "format", "key", "value"}` of the kinds `gold-answer` and `switching-value` at `<kind>/sha256/<hex>`, the hash of the key's canonical bytes: `write` refuses with `invalid-entry`, `unknown-kind` and `held-key`, and `lookup(kind, key)` returns the entry or `None`, refusing a file that is not that entry with `misfiled-entry`. Each file is written whole by exclusive create. `RefusalReason` gains the eight reasons, and `EvaluationRefusal.key` holds a design hash or an evaluation key's members.
- The `Known` cell: a table cell, `Known` in the notation and `{"known": true}` in the document, matches any value, null included, and no marker. A row failing on it does not meet marker rule 2, so a row holding `Known` over an input gives way to the next row when that input is down; the input's entry keeps its marker. In a design written in Python, a label spelt `Known` is now written `{"is": "Known"}`.
- Groups give their reasons: `Group(refs, reason)`, `reason` a non-empty list of `convergent`, `discriminant`, `exclusive`, `exhaustive` and `consistent`, a misspelt or repeated one refused at load (check 9). The document holds a group as `{"refs", "reason"}`. "Correlated group" is now "group".
- A value cell (`is` or `one_of`) over a `pick_with_margin` or `pick_with_thresholds` input whose question has a candidate-valued label set may name one of its fixed labels, such as `none`; the input stays `string`, and a cell naming any other value still fails check 9, now listing the fixed labels.
- The lint and the lens over grounded forms: a grounded `t:` source's entries range over their declaration's points. A cell over a `candidate` read adds nothing to the grid. The lens links a `candidate` read to the set's card.
- Grounded sources of `t:` refs: a source grounded over a candidate set provides each `t:` ref once per candidate, under the grounded refs the engine forms and passes in `refs`; a binding reads each one's candidate with the new `ommat.bindings.candidate_of`. Each value is checked alone. A per-candidate question may hold a slot on a declared ref grounded over its own set, filled from that candidate's entry and given to the binding as a need under the grounded ref; a marker there leaves that candidate's question out.
- Grounded rules and tables: a function rule or a table declared `grounded=ref` over a candidate set runs once per candidate, reading `candidate`, `candidate.f` and the current candidate's entry of a declared ref grounded over the same set, and writes one entry per candidate at `d:x["<candidate>"]`, each with its own `derivation` or `rows`. A set holding a marker gives the declared ref the set's need marker, and an empty set writes nothing. A reader of the declared ref gets a `dict` by candidate value. Load refuses a `candidate` read outside a grounded component, a field it does not name, a table reading a grounded ref of another set, a field path on a grounded ref outside its set, and a grounded candidate set.
- Candidate sets of records: a candidate set may be a list of a record type whose `candidates` member names its candidate field, a `string` field, each other field a scalar, a scalar or null, or a list of a scalar. Its members are distinct by their candidate values; a per-candidate question's grounded refs, a candidate slot, a candidate-valued label set's labels, the read view's `dict` and an `in` cell over the set all go by the candidate value. The record's `settings` item names each set's candidate field under `sets`, null for a `list<string>` set, and `redact` digests a record candidate under its field's class. Load reserves the name `candidate`.
- Decision tables. A rule, the policy among them, may be a `Table`, under the hit policies `U`, `A`, `P`, `F`, `C+`, `C<`, `C>` and `C#`. An input is a read or a `Helper` calling `pick_with_margin`, `pick_with_thresholds`, `size`, `mass` or `extract` over one; a cell is written in the spec's notation (`-`, `Unsure`, `>= urgent/bar`, `[lo, hi]`, `{a, b}`, `in d:x`, a label) or the tagged form load writes in the document; an output is a value, `Unsure`, `Input(ref)` or `Param(path)`. A data rule is a one-input table. A table's entry holds `rows`, every matching row, and the marker contract's two rules pass an input's marker on. Load checks every cell, output and hit policy, and refuses overlapping rows under `U`, and under `A` when their outputs differ. The answer grid takes a table's comparisons, integer value cells and helper bindings, an integer literal included, and the dead-question lint runs over tables. The lens shows a table's inputs as its reads. A cell may list marker kinds, `Unsure or Unavailable` or `Undetermined` for all three, so one row takes an optional input's outage. `Helper`, `Input` and `Param` are public.
- The lens at scale: a selection in the Design or Turn view brings its links to the top of each column and folds the rest into a stub per column that says how many and why, never "unrelated", with a control to dim them in place instead; a page with a column past 40 cards turns compact, each card keeping its value on one line, its bars, a call's outcome and its boundary notes; an answer's labels past its leader and runner-up fold into one "Other" bar, keeping every label a threshold or mass bound names, and a call's long question list folds after four; a selected answer's question opens in the Turns view with "Compare across turns".
- The lens's Design and Turns views. `ommat.lens` shows a design with or without a record: its targets, questions, rules, the policy among them, and parameters, and the lineage of any card, a target's questions, latent links by role and estimating rules included, the rest dimmed as having no link declared. A turn's entries show their targets, and its answers the bars, thresholds, margins and mass bounds their design declares. The Turns view tables the records by design hash or by question identity. `python -m ommat.lens` writes a page for a design alone.
- Targets: a design may declare `targets={id: Target(statement, values=None)}`, the properties of the state its questions and rules are about. A `Question` takes `target`, the target it asks about, and `latent_targets`, each `{"target": id, "role": TargetRole}` with the role `reflective`, `formative` or `unknown`; a `Rule` takes `target`, the target it estimates. They guide a reader and gate nothing: no turn reads one, and a question's identity leaves them out. Load refuses an undeclared target id, a question's own target as latent, a link repeated under one role and a member of another form. `Target` and `TargetRole` are public.

### Removed

- The context block and the handoff. From `ommat`: `Context`, `ContextEntry` and `handoff`; from `ommat.conversation`: `handoff_text`. `Design` loses `context`, the design document its `context` member, and a record holds no `context` item. `FindingKind` has no `context`. `transcript` and the renderers stay. The how-to `hand-off-context.md` is replaced by `hand-off-a-turn.md`.
- The plan, the guard and the reference runner. From `ommat`: `Plan`, `PlanKind`, `Step`, `Origin`, `Binding`, `PlanDeclaration`, `Policy`, `PolicyTable`, `Requirement`, `Verdict`, `VerdictKind` and `GuardFailure`; from `ommat.helpers`: `run_plan`, `RunRefusal`, `BindingNotFound` and the `unsure_to_execute` lint. `Design` loses `requirements`, `default_deny`, `tools` and `plans`; `Decision` loses `plan` and `verdict`; `FindingKind` loses `plan` and `verdict`. A policy table is an ordinary `Table`. Compile, the seven plan rules, plan declarations, declared `reason` and `reply`, and default-deny go with them; `SourceRequirement` and the `refused` cause stay.
- The `calibrated` provenance detail, a provider's own claim that its probabilities are calibrated, which nothing checked. `CallResult` and `RequestProvenance` no longer take it, so a binding passing `calibrated=` gets a `TypeError`; `call_result` no longer folds it; the conformance kit no longer checks it; and the idia binding drops idia's `calibrated` from the call, its reason and its claim included. Record format 7 holds it nowhere, and the ledger refuses it there as a `calls` entry's member, a `missing` or `invalid` key or a `claimed` name; a record of formats 5 and 6 reads with it as before.

## [0.4.0] - 2026-10-23

### Added

- Per-candidate picks: `ommat.helpers.pick_each_with_margin(r, ref, bar, margin)` and `pick_each_with_thresholds(r, ref, thresholds, margin)` read a per-candidate question's declared ref and return a new `dict` in the set's order from each candidate to its pick, to `Unsure` with `abstained` naming that candidate's grounded ref, or to its entry's marker unchanged, so a rule weighing every candidate no longer takes the argmax itself.
- A how-to, [Gate a source on an earlier estimate](docs/how-to/gate-a-source.md): a source requirement over a label-valued projection asks a later source only when an estimate holds a value, without sending the estimate, so `oracle_binding(provider, state=...)` still applies.
- `unsure_to_execute` runs an abstention search: for each question a rule on the policy's lineage, through the dependency graph, reads, or each candidate of a per-candidate one, it runs whole turns with that question, the subject, at its abstention point, every label 0 or a null extraction value, on which every pick and `extract` abstains, and reports a run whose plan is `execute` while a lineage rule returned a pick or `extract` over it. Reads the lineage rests on range one at a time from their first points and others hold one point, and each subject stops at its first finding, so the search grows with the sum of the reads' points, not their product. Once a lineage rule reads a question, the lint needs the free inputs `dead_questions` needs; a missing one is a `ValueError` naming every unfilled read.
- A spec section on source requirements: what a `SourceRequirement` declares and reads, that its ref orders the source and is not sent unless it is also a need, what the gated source gets, and the load checks that apply.
- `ommat.helpers.determined(r, *refs)` returns a `tuple` of its reads' values, or the marker of highest precedence among them unchanged, so a rule passes a read's marker on without testing each read.
- The context block and the handoff: a design may declare `context=Context(entries, plan=True, steps=True, record=True)`, each `ContextEntry(ref, text)` flagging `t:state` or a `d:` ref, with or without a field path, and wording it with a `Text` whose slots name refs or parameters. Compile renders the block into the `plan` item's new `context` member, an entry holding a marker instead of text when a slot reads one, and replay checks it byte for byte. `handoff(record)` gives the next reader the design, the record hash, the plan's kind, text and verdict kind, its steps with each argument tagged and resolved, only under a passed verdict, and the entries, each part under its switch; it never holds the guard's failures, a requirement, a probability or provenance. Load refuses a duplicate flagged ref, a `q:` ref, a slot over an `identifier` class and a text with no slot naming its flagged ref. `redact` digests each rendered text and the design's name. A how-to, `docs/how-to/hand-off-context.md`, shows it with the transcript and both renderers, with its examples and test in `docs/how-to/hand_off_context/`.
- The transcript: `transcript(record)` gives every source call of a turn and its conclusion, unworded, for an LLM conversation: each call's asked refs, recorded outcome and answers, the board's estimates, the plan, the verdict and the context entries as recorded, each value and marker tagged, and a passed `execute` plan's steps with their resolved arguments when it binds no earlier result. Each id is `om_`, 24 hex digits of the record hash and `_c<n>`, `_d` or `_s<n>`, so it fits a provider's tool-call id. It holds no `t:state`, provenance, prompt or derivation.
- `ommat.lens`, outside the compatibility promise: `page(records, designs=(), *, skipped=())` renders stored records as one self-contained HTML page, each round's calls and entries, the answers as percentages, the plan and the verdict, with the lineage of any entry, call or the plan a click away: from the record, and, with the design paired by its hash, from each rule's and the policy's declared reads and each source's needs, requirement, candidate set and the refs its questions read. `python -m ommat.lens PATH [-o FILE] [--open]` writes it for a record file or a folder of records and designs. The page loads nothing from the network and holds the records whole, user text included, so keep it as you keep them.
- `ommat.conversation`, outside the compatibility promise, wording nothing: `handoff_text(handoff)` renders a handoff as labelled lines for a model's instructions, and `to_chat_completions(view, *, turn=None)` renders a transcript as Chat Completions messages, each source call and decide a tool call with its result and the pending steps calls for the caller to run. `ommat[pydantic-ai]` adds `ommat.conversation.pydantic_ai.to_model_messages(view, *, model_name=None, provider_name=None, turn=None)`, the same as Pydantic AI messages, a failed call's return marked `outcome="failed"` and each response stamped, so an agent run with the history runs the pending calls with its own tools. The source calls and decide are marked as ommat's bookkeeping, and the pending calls not; each module's `is_bookkeeping(message)` tells one, and each module's `drop_earlier_bookkeeping(messages)`, the Pydantic AI one a history processor, drops an earlier turn's bookkeeping, each call with its result. Both renderers take an optional `turn`, which stems every id afresh, so one record rendered for two turns repeats no id. Every JSON string they write is in the ordered encoding, each object in the order the record holds it. A source's tool name maps `/` to `-`; a name no provider takes is a `ValueError`.
- The provenance profile: each call item states who answered and how, `provider`, `model_requested`, `model_reported`, `revision`, `runtime`, `elicitation`, `precision` and `prompt`, hashed, with `claimed`, the details the source asserts and cannot verify. A call that sent a request gives each detail a value or a reason in its `calls` entry's `missing`, from `not-reported`, `not-pinned`, `not-sent`, `hidden`, `not-applicable` and `not-exposed`, beside `request_id`, `calibrated` and `clients`, the versions of the libraries that made the call. `precision` may be `"unrounded"` or `{"step": "0.05"}` as well as decimal places. The idia binding maps idia's outcome onto it, a call whose requests name one package at two versions `Failed` with `invalid-return`, and the conformance suite's new `provenance` check holds a binding to it.
- Measured wording in, the same wording out: a `noul` may declare `yes` then `no` with at least one described, and a question's wording may be `ommat.Structured(template, slots)`, a JSON object or array whose string values are templates, its objects kept in the order written. Both reach a binding through `RenderedQuestion`, the idia binding sends them as idia takes them, and a provider whose capabilities carry neither form refuses that question alone, `unsupported`. An undescribed `noul` and a `Text` wording keep their bytes and identities.
- Candidate-valued label sets: a `choice` declared with labels `{"fixed": [...], "candidates": ref, "at": k}` is asked over its fixed part with the members of a `list<string>` candidate set placed after its first `k` fixed labels (by default after all of them), a source's `t:` ref declared `{"type": list<string>, "candidates": True}` or a rule's `d:` ref with `candidates=True`, rendered each time it is asked. The set's members are distinct, a repeat `invalid-return`. A question whose set is a marker, is empty, renders too many labels or holds a fixed name is left out of its batch, `call` null, with `need-unavailable` or `need-undetermined`, `when-false`, the new `CauseCode.label_overflow`, or `label-collision`, naming the set. Replay's `question-changed`, `from_record`, the redacted view, the dead-question lint, the idia binding and the conformance suite each handle it. A candidate set of records stays refused at load.
- Per-candidate questions: a source declared `grounded="<ref>"` over a `list<string>` candidate set, a source's `t:` set or a rule's with `candidates=True`, asks each question whose wording holds a slot `{"candidate": <ref>}` once per candidate, in the same request as its other questions, which are asked once. Each is asked under its grounded ref, `q:x["<candidate>"]`, the candidate as RFC 8785 writes a string, its wording rendered with the candidate, and one question identity covers every candidate. A rule reads the declared ref and gets a `dict` from each candidate, in the set's order, to its `Answer` or marker, or the set's need marker when the set held one; reading it also reads the set. An empty set asks nothing for the question. The set is a need only when declared. A choice helper reads one ref's answer, so a rule works on the `Answer` objects in the `dict`. Load still refuses grounded rules, grounded `t:` sources, a per-candidate extraction question or one over a candidate-valued label set, and a need or slot ref on a per-candidate question's declared ref. Over an empty set nothing is asked for that question, and a source left with nothing to ask is not called, its `when` not run, and not charged. Load refuses a group mixing grounded and ungrounded `q:` refs or refs over different sets.
- The record's `settings` item holds `grounded`, each per-candidate question's declared ref mapped to its set's ref, `{}` when the design grounds nothing; a format-6 record requires it. The call item keys a per-candidate question's one `questions` entry by its declared ref.
- `dead_questions` grounds a per-candidate question's entries from its set at each point, varying them fastest, reports it once under its declared ref, and has a new status, `not-grounded`, for a per-candidate question that no point grounded; it raises `ValueError` when a `d:` set differs between runs of one assignment, which it cannot fix.
- A how-to, `docs/how-to/add-a-source.md`: a new source answered through an idia provider, idia's `gliner` leaf among them, or by a binding of your own over a model in your process, with its example and test in `docs/how-to/add_a_source/`.
- A tutorial, `docs/tutorials/decide-with-idia.md`: the street-reports design decided with OpenAI's Decisions and Cloudflare's Clairic through `ommat[idia]`, each call's record read, replayed, and answered again from a stored record. Its script is in `docs/tutorials/decide_with_idia/`, and its test replays the live run from recorded logs.
- `ommat[idia]` and `ommat.bindings.idia`: `oracle_binding(provider, *, state=None)` binds an oracle to a provider through an idia `Dispatcher` over one leaf, one idia request per source under the call's `seconds`, each object sent in the order it is received, each answer, refusal, fault and failed request mapped to the value or marker ommat takes. `state` names a need that a label source sends as the whole JSON part, its value alone in place of an object keyed by refs, so a caller sends the state shape it measured a provider on; a label source that needs it beside another need, images aside, is `unsupported`, and a `state` that is not a non-empty string is a `ValueError`. Install it with `pip install "ommat[idia] @ git+https://github.com/CRSiegfried/ommat@v0.4.0"`, after idia 0.1.0 with the extras for its providers, as the README shows.
- `seconds`: interpret calls each binding as `binding(batch, seconds=s)`, `s` the time the call has, the smaller of the batch's timeout and the time left to the deadline. A binding converts it to its provider's deadline. A binding that does not take the keyword raises `TypeError` at its first call, so the call is `Failed` with `raised` on every ref of the batch.
- A binding may mark a ref `Unavailable` with `timed-out` or `raised` when the provider request that carried it ran out of time or failed, with the request's status and message as `warnings` lines; the other refs of the call stand, and the call is `returned`. Under a `returned` call these markers are the binding's; on a `Failed` call, the engine's. Replay returns them as recorded.
- The image need: a need whose value is exactly `{"media_type": ..., "data": ...}`, `media_type` naming an image media type such as `image/png` and `data` the image's bytes, declared `record(media_type=string, data=bytes_)`, is an image; a binding whose provider takes images sends it as one, and `ommat.bindings.image_need` reads it.
- `ommat.bindings`, the binding kit, what a binding author calls, which `import ommat` does not import, its eight names public under the same deprecation rule as `ommat.__all__`: `OracleBinding`, the type of a binding, `async def binding(batch, *, seconds)`, which `oracle_binding` returns; `RequestProvenance`, one request's provenance, which `call_result` folds; `extraction_value(value, guess, p_null, confidence, span)` returns the five-member dict an extraction question's ref takes, with each `date`, `time`, `datetime` and `timedelta` written in ommat's grammar, and raises `ValueError` for a value the grammar cannot hold; `bounded_warnings(lines)` returns a `warnings` tuple that conforms, escaping surrogates, leaving out blank lines, and past either bound ending with a line counting those left out; `json_value(value)` returns a need's value in record form, each answer as its document and a tuple as a list, and raises `TypeError` for `bytes` at any depth; `image_need(value)` returns an image need's `(media_type, data)`, or `None`; `prompt_text(prompt)` returns a mapping prompt as `json.dumps(prompt)`, its keys in the order given at every depth, raising `TypeError` for a key that is not a `str`, and a `str` or `None` as given; `call_result(values, requests, *, precision, warnings=())` folds each request's `RequestProvenance` into the call's `CallResult`: its distinct string details and `request_id` one per line, `runtime` and `clients` merged, a package at two versions a `ValueError`, `claimed` the union, `calibrated` false when any request says false, `missing` a reason only where every request lacks the detail, `usage` and `attempts` summed, `truncated` sorted, and no provenance when no request made an attempt. The idia binding uses the other seven.
- `ommat.bindings.conformance.check(binding, *, batches=None, deterministic=False)`: the binding conformance suite. It calls a binding with the given batches, or with its own covering each answer kind, an image need, a `t:` source, a candidate-valued question and a per-candidate question, and returns the protocol's failures as strings naming their check: `seconds`, `returns`, `values`, `markers`, `answers`, `per-ref-cause`, `warnings`, `precision`, `provenance`, `unsupported-provenance` and `deterministic`, which ignores `request_id`; an empty list passes.

### Changed

- `unsure_to_execute` runs the abstention search whenever a rule on the policy's lineage reads a question, which breaks callers of earlier releases three ways: a call without `values` for the free inputs the search's turns need, such as a `t:state` string field or a tool result, raises `ValueError` naming every unfilled read, and a `values` key for a read the lint's grid or types already fill is refused; the report gains an item per question whose abstention a lineage rule drops, beside the `d:` items, so a marker passed on to the policy is reported under both; and `points` counts the search's runs, which grow with the number of questions times the sum of the ranging reads' points.

- The helper version is 3, for the per-candidate picks and `determined`: a record of version 2 replays with a `helpers-mismatch` finding beside any other, and every record hash changes.
- jurat is renamed Ommat: the distribution, the package and the import are `ommat`, and the extra `ommat[idia]`.
- Key order is kept from declaration to wire to record, since the order of an object's keys is part of what a model reads. `ommat.types.record(b=..., a=...)` spells `record{b: ..., a: ...}`, its fields in the order declared, where it sorted them; a record value's fields stand in its type's order, and every other object keeps the order its author or producer gave it. A slot that renders an object writes it in that order, where it wrote canonical JSON.
- Records and design documents are format 6, each number moving only with its own document's rules. A design document holds a source's `payload_order`, a parameter leaf's `order` and, when its template is out of canonical order, a structured wording's `order`; a record's `entry`, `plan` and `verdict` items each hold `order`, an order object the ledger derives, beside canonical bytes that still sort. `Record.log`, the observer and replay give each object in the order its item's `order` holds, and replay compares items with `order` included, so a rerun that holds an object in another order is a finding. Every design hash and record hash changes, so golden hashes must be updated. `read_record` reads record formats 1 to 6 and `load` loads design documents of formats 1 to 6 to their own hash; a design before format 6 spells a record's fields in code-point order and holds no order member, and one before format 5 declares no context block; a record before format 6 holds no `order`, and one before format 5 holds no `context` in its `plan` item; a record before format 4 holding a binding's `timed-out` or `raised` under a `returned` call is refused, and one before format 5 holds `snapshot` in place of the provenance profile.
- `CallResult.snapshot` and `RequestProvenance(snapshot=...)` are renamed `revision`, beside the profile's other details; a call item from format 5 holds `revision` and no `snapshot`. `call_result` reads only the requests that made an attempt. A binding passing `snapshot=` now gets a `TypeError`.
- A call result's provenance is tested at the write: a provenance string, a `runtime` or a `claimed` off its form, or a `claimed` naming a detail that holds no value, fails the call with `invalid-return`; a `request_id`, `calibrated`, `missing` or `clients` off its form, a `missing` giving a reason for a detail that holds a value among them, fails nothing, its repr kept under `invalid`. The redacted view digests a call's `request_id`.
- decide and replay refuse an async observer with `EntryRefusal`, where its coroutine was dropped unawaited: an `async def` function or async generator function, a bound method or `functools.partial` of one, or an object whose class defines one as `__call__`.
- A binding is `async def binding(batch, *, seconds)`: every binding must take the keyword. The fixture binding, `from_record` and the tutorial's binding take it and ignore it.
- The tutorial's binding, `fixed_answers`, reads a `score` by its kind and marks a `t:` ref it does not answer `unsupported`, so it passes the conformance suite's own batches; the tutorial says what `seconds` is for.
- `precision` is the provider's declaration, recorded, and the engine does not check probabilities against it; a `noul`'s `no` is held as the binding's provider library derives it, neither rounded.
- `SourceCall.questions` keys a per-candidate question by each grounded ref, `q:x["<candidate>"]`, so a binding that looks a question up in the design by its key, or parses a ref by searching for `]`, must take the bracketed string off with a JSON parser first.
- The ledger and `read_record` admit a grounded ref as an entry's `ref`, in a cause's `refs` and as a `calls` entry's `sums` key or `truncated` ref, where they refused one everywhere; `redact` digests each candidate inside a grounded ref under its set's class. Replay grounds again from the set's entry and names a per-candidate question by its declared ref in `question-changed`, and `from_record` compares it with the stored call item's entry under that ref, answering the source's other refs and marking `unsupported` a candidate the stored turn did not ask.
- `RenderedQuestion.wording` is `str | dict | list`: a structured wording reaches a binding as a JSON object or array, so a binding that treats it as a string, `wording.strip()` among them, must handle the other two.
- `Question.labels` may be a mapping, `{"fixed", "candidates", "at"}`, for a candidate-valued label set, as well as a sequence or `None`; code that reads a design's labels as a sequence must handle it.
- `RenderedQuestion` and `SourceCall` check their fields when built, raising `TypeError` for a field of the wrong type and `ValueError` for a wrong value. `kind` and `value_type` take a member or its string and hold the member; a `noul` question's labels are `yes` and `no` and an extraction question's none; `descriptions` is as long as `labels`; an extraction question needs its `value_type` and `text`, and a question of another kind leaves its extraction members unset; a source call's `refs` and `questions` are not both non-empty. A string subclass is held as its string data. `CallResult` still checks nothing.
- `use_answers` compares the two records' state entries and `settings` items as replay compares items, `order` included, an item of a record before format 6 compared without `order` and `grounded`, and reads a plan finding that differs only in `context` with the plan's `order` taken over the rest alone.
- `from_record` compares a need with the stored record's by its ordered encoding, from record format 6, and bounds its `warnings` with `bounded_warnings`, and refuses with `unsupported` a source whose need is not a ref or holds a value outside the value domain, where it raised.
- Load check 4 refuses a source that provides no ref: a source provides one or more `q:` or `t:` refs. A design with such a source loaded before and now raises `InvalidDesign`.
- The redacted view digests a requirement's value, on a plan's step and in a refused verdict's failure, under its ref's class tree, as that ref's entry is; the value was open.
- The public API is what `ommat.__all__` lists and the `__all__` of `ommat.types`, `ommat.helpers`, `ommat.evaluation` and `ommat.bindings`, all under one deprecation rule. `ommat.bindings.conformance` and `ommat.bindings.idia` stay outside it and follow idia while idia is 0.x, and `ommat.conversation` and `ommat.conversation.pydantic_ai` stay outside it while they are validated.

### Fixed

- A rule may return a marker whose cause names a grounded ref the turn wrote, such as one candidate's abstention, and a `plan` item's cause and context-entry markers may name one. Before, the first was `invalid-return`, and a flagged `d:` carrying such a marker broke the turn at compile's write. `redact` digests the candidate in each place.
- A `-0.0` a binding, a rule or the policy returns is held as `0.0` on the board, in an answer, in the plan and in the record's stored copy, where it stayed `-0.0` live while the record wrote `0` and replay read back `0.0`, so a rule that told them apart diverged in replay.
- The design lints probe both integers either side of a boundary that is not integral on an integer read, where they dropped it and could miss the values below or above it, so `dead_questions` could call a live question `no-change-found`.
- `t.list_`, `t.mapping` and `t.record` raise `ValueError` for a type nesting past the depth bound, where they returned a string load refused.
- `run_plan` runs a decision whose record holds a marker entry, where it raised `KeyError` before the first tool call.
- A marker a rule returns is `invalid-return` when a ref of its cause is not a ref the design provides, a source, rule or tool name, a parameter path, `policy`, `codec`, `rule:N` or `step:N`, where it was written as given: free text in a cause reached the record's hashed log and stayed open in the redacted view.
- `load` gives a function whose `__wrapped__` chain loops a null source hash, as for any function whose source cannot be read, where it raised `ValueError`.

## [0.3.0] - 2026-10-22

### Added

- A tutorial, `docs/tutorials/write-a-design.md`: one offline design taken through `load`, `decide`, the record and replay, its example tested. Its example files are in the repository at `docs/tutorials/write_a_design/`, for a reader who installed jurat from an index.
- Label descriptions: a `choice` or `score` label may be `{"name": ..., "description": ...}`, which the design document, the call item and the question's identity hold as declared. `RenderedQuestion.descriptions`, keyword-only, gives each label's description aligned with `labels`, `None` where a label has none. Answers, the answer grid, the lints and the `boundaries` checks read names only.
- `CallResult.warnings`: the binding's own lines about the call, recorded under the call in `unhashed` and outside every hash. A malformed value is kept in `invalid` and is never a fault.
- `CallResult.precision`: the decimal places the provider rounds probabilities to, hashed on the call item. A value that is not `None` or an integer from 0 to 17 is `invalid-return` for the whole call.
- `CauseCode.unsupported`: the marker a binding returns for a ref it will not put to any provider, with the reason as a line of `warnings`. It is the 24th cause code. A rule that returns the marker it read provides it unchanged, so `unsupported` stands on a `d:` entry with its refs as any binding code does.
- The record document's `hash` member: the record hash over the log. `read_record` recomputes it and refuses a document whose `hash` is missing or does not match.
- `jurat.evaluation`, the evaluation subpackage, with its first job: `use_answers(record, loaded, other)` and `use_answers_sync`, which rerun `record`'s turn under `loaded` with `other`'s calls answering and return `{"other", "findings"}`, `other` its record hash and the findings replay's. Both records are a `Record` or a stored document and must be finished turns of the loaded design with the same state entry and `settings` item. Each refusal is an `EvaluationRefusal`, its `reason` a `RefusalReason`; a replay record is a valid `record` or `other`, so two models decided under different parameter sets compare by replaying the second under the first's loaded design.
- `jurat.from_record(record, loaded)`: an oracle binding that answers a live turn's sources from a stored record, refusing with `unsupported` a source with no returned call or different needs, a changed question, a ref with no stored entry and a recorded marker other than `invalid-answer` or `invalid-return`, with null provenance and a `warnings` line naming the record's hash.
- `ReadView`, the view a function `when`, rule or policy is called with, is public, so a component can be annotated with it. `When`, `Rule` and `Policy` type `function` as `Callable[[ReadView], object]`, so a lambda passes pyright strict.

### Changed

- Records and design documents are format 3. Every design hash and record hash changes, so golden hashes must be updated. Every format-3 call item holds `precision`.
- An exception's recorded traceback starts at the component's own frame and names each file by its module, so the record holds no local paths from the traceback.
- `read_record` reads format-1 and format-2 records and `load` loads format-1 and format-2 design documents to their own hash, each under its format's rules. A format-2 record holding a described label, `precision`, `warnings`, `unsupported` or a `hash` member is refused.
- `Step` takes its arguments as any `Mapping`, read once through `items()`, and still keeps a read-only copy; a non-mapping is a `TypeError`. The recorded plan is unchanged.
- Check 4's message for a rule that provides another ref names the rule's own `d:` ref, and for another rule's `d:` ref, whose it would be.
- A `load` refusal for a type that does not fit names the type as written: check 9's text and `reference_date` refs, check 10's state declaration and parameter shape, check 8's boundary leaf, and check 9's boundary key and role leaves.

## [0.0.1] - 2026-10-20

### Added

- The design types: `Design`, `Source`, `Question`, `Text`, `Rule`, `Policy`, `When`, `Requirement`, `SourceRequirement`, `Group` and `Parameter`, with `Table`, `PolicyTable` and `PlanDeclaration` for the forms `load` refuses in this release.
- `jurat.types`: constructors for the type a field holds (`boolean`, `integer`, `number`, `string`, `bytes_`, `label`, `list_`, `mapping`, `record` and `nullable`).
- `load`: checks a `Design`, or its canonical document, before any turn runs and returns a `LoadedDesign`; an invalid design raises `InvalidDesign` naming each failed check.
- `decide` and `decide_sync`: one turn, interpret over rounds of sources and rules, then compile with the policy and the guard, returning the plan, the verdict and the record. Rules and the policy are Python functions.
- `RunSettings`: the run settings, with a round bound of 8 and a 60 s timeout by default; `EntryRefusal` for a wrong argument at `decide`'s entry, raised before any record is written.
- The markers `Unsure`, `Unavailable` and `Unasked`, each with its cause, for every value a turn could not settle.
- The record: its canonical JSON encoding and hashes, the observer, and `read_record` for a stored record, which raises `InvalidRecord` for one it cannot read.
- `replay` and `replay_sync`: a recorded turn rerun under a loaded design with no model call, reporting each difference as a finding.
- The record views: `escalation` and `redact`.
- The binding protocol between the engine and a model adapter: `SourceCall`, `RenderedQuestion` and `CallResult`.
- `jurat.helpers`: the choice helpers and combinators rules call, the design lints `dead_questions` and `unsure_to_execute`, and the reference runner `run_plan`, which raises `RunRefusal` for a plan it refuses before calling any tool and returns `BindingNotFound` for a step argument whose binding missed.
- Project scaffolding: package, license, code of conduct, contributing and security policies, CI.

### Not included

- `load` refuses decision tables, policy tables, data rules, plan declarations, candidate sets, candidate-valued label sets and grounded declarations.
- No state carries from one turn to the next.
